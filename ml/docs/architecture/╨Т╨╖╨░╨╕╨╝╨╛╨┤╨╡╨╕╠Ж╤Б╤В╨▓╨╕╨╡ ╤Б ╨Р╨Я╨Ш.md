# Взаимодействие с API

Контракт для бэка клиентского кабинета и CRM. Базовый адрес при запуске Docker Compose: `http://127.0.0.1:8000`. Актуальная машинная схема находится на `/openapi.json`, форма для ручных запросов — на `/docs`. Реализация маршрутов: `src/app/main.py`; ограничения полей: `src/app/schemas.py` и `schema.py` каждого сервиса.

## Общие правила

- Все `POST`, кроме загрузки документов, принимают `application/json`. Неизвестные поля Pydantic-моделей запрещены.
- `case_id` в новых сценариях имеет демонстрационный вид `DEMO-[A-Z0-9-]` длиной до 24 символов после префикса. Не отправляйте реальные ИНН, ФИО и документы.
- `risk_probability` и `cash_gap_probability` лежат в `[0, 1]`, но описывают разные демонстрационные риски. `preliminary_approval_probability = 1 - risk_probability` в Credit Advisor не является вероятностью решения банка.
- Сервис не хранит запрос и не меняет статус заявки. Черновики для клиента проверяет сотрудник до отправки.
- При ошибке валидации FastAPI возвращает `422` со списком ошибок в `detail`. Доменный `ValueError` тоже даёт `422`, но `detail` в этом случае строка. Некорректный ответ LLM даёт `502`; отсутствие ключа или сетевой сбой OpenRouter — `503`.

| Доступность без OpenRouter | Маршруты |
| --- | --- |
| Да | `/health`, `/v1/scoring`, `/v1/nba/recommendations`, `/v1/cash-gap/forecast`, `/v1/assistant/search`, `/v1/offer-recovery/recommendations`, все `/ml/*` |
| Обычно нет | `/v1/underwriting/summary`, `/v1/decision-explainer/refusal`, `/v1/crm-copilot/reply`, `/v1/documents/parse`, `/v1/assistant/answer` |
| Зависит от кандидатов | `/v1/credit-advisor/recommendations`: при пустом списке допустимых продуктов вернёт `200` без LLM, иначе нужен ключ |

## Профиль, риск и продукты

### `POST /v1/scoring`

Обязательные поля: `product_id`, `requested_amount > 0`, `term_months > 0`, `business_age_months >= 0`, `monthly_revenue >= 0`, `net_margin_percent` от 0 до 100, `debt_to_revenue_ratio >= 0`, `has_overdue_debt`, `credit_history_score` от 0 до 1000, `has_collateral`, `legal_form` (`ip` или `ooo`). `product_id` должен входить в кредитный каталог.

Ответ: `risk_probability`, `risk_band`, `factors[]` (`feature`, `contribution`), `model_version`. Положительный вклад повышает логит риска; это не денежный вес и не процент одобрения.

```bash
curl -sS -X POST http://127.0.0.1:8000/v1/scoring \
  -H 'content-type: application/json' \
  -d '{"product_id":"business_loan","requested_amount":2000000,"term_months":36,"business_age_months":28,"monthly_revenue":1500000,"net_margin_percent":18,"debt_to_revenue_ratio":0.8,"has_overdue_debt":false,"credit_history_score":720,"has_collateral":false,"legal_form":"ip"}'
```

### `POST /v1/credit-advisor/recommendations`

Принимает финансовые поля скоринга **без** `product_id`, плюс обязательные `purpose`, `has_marketplace_sales`, `has_existing_business_loans`; необязательные `context_tags[]` и `top_n` (1–11, по умолчанию 3). Продуктовые правила из кредитного CSV сначала отсекают неподходящие варианты. Скоринг каждого оставшегося кандидата выполняется локально. LLM может только изменить порядок и написать `reason`, но не добавить продукт.

Ответ: `recommendations[]` с `rank`, `product_id`, `preliminary_approval_probability`, `risk_probability`, `context_relevance`, `combined_score`, `reasons[]` от правил и `reason` от LLM; `excluded_product_ids[]`; `model`. Если допустимых продуктов нет, `recommendations=[]`, `model=null`, HTTP `200`, вызова OpenRouter нет.

### `POST /v1/nba/recommendations`

Принимает `legal_form`, возраст бизнеса, `monthly_turnover`, `monthly_payment_count`, `online_sales_share` от 0 до 1, `employee_count` и признаки счёта, сайта, офлайн-точки, маркетплейсов, ВЭД, налоговой отчётности, электронных документов и регистрации бизнеса. `existing_product_ids[]` и `top_n` (1–18, по умолчанию 3) необязательны. Ответ — массив `{product_id, score, reason}` только из некредитного каталога. Сетевых вызовов при расчёте нет.

### `POST /v1/cash-gap/forecast`

Обязательные поля: `monthly_revenue`, `net_margin_percent`, `opening_balance`, `monthly_fixed_costs`, `sales_volatility`, `payment_delay_days`. Необязательные: `upcoming_expenses=0`, `simulation_seed=20261022`, `forecast_days=30` (1–365). Движок сначала генерирует синтетическую историю, затем считает прогноз. Ответ: `cash_gap_probability`, `risk_band`, `estimated_shortfall`, `forecast_days`, `factors[]`.

## Финансовый двойник и кредитный квест

Этот локальный поток работает без LLM. Начните с `GET /ml/demo/risky` для полного синтетического JSON. Его `forecast_request` отправьте в `POST /ml/forecast`. Ответ передайте как `forecast` в `POST /ml/simulate`; поле `loan` берётся из демо-профиля. Для сравнения без кредита отправьте тот же `forecast` без `loan`. Весь исходный JSON демо-профиля отправьте в `POST /ml/quest/generate`, затем дополните его одним `plans[i].actions` и отправьте в `POST /ml/quest/recalculate`.

В истории обязательны 6–36 последовательных месяцев `month`, `revenue`, `operating_expenses`, `taxes`, `existing_debt_payment`, `cash_balance`; `horizon_months` — от 1 до 12. `loan` задаёт сумму, срок, ставку, цель, инвестицию и ожидаемый ежемесячный эффект отдельно. Сумма и срок `loan` должны совпадать со `scoring`; выручка последнего месяца и возраст бизнеса также должны совпадать. Произвольные, не выданные генератором квеста действия отклоняются с `422`.

`/ml/simulate` возвращает денежные остатки и минимальный остаток по каждому сценарию, без вероятности кассового разрыва. Её отдельно оценивает `/v1/cash-gap/forecast` на своём дневном профиле. `baseline_score` и `projected_score` — отображение риска действующего `ScoringEngine` на шкалу 0–100; это не вероятность одобрения. Формулы и ограничения описаны в [README финансового модуля](../../src/financial_intelligence/README.md).

## Документы и профиль

### `POST /v1/documents/parse`

`multipart/form-data`: строковое поле `case_id` и от 1 до 8 повторяемых полей `files`. Каждый файл — PDF, PNG или JPEG до 10 000 000 байт с соответствующей сигнатурой. Один документ ограничен 20 страницами, общий распознанный текст — 60 000 символами. Идентификаторы `doc-1`, `doc-2` и далее присваивает сервер в порядке загрузки.

```bash
curl -sS -X POST http://127.0.0.1:8000/v1/documents/parse \
  -F 'case_id=DEMO-001' -F 'files=@./demo-statement.pdf;type=application/pdf'
```

Ответ содержит:

| Поле | Значение |
| --- | --- |
| `profile` | Универсальные поля: `legal_form`, `tax_regime`, `tax_id`, `registration_number`, `industry`, `business_age_months`, `monthly_revenue`, `monthly_expenses`, `net_margin_percent`, `existing_debt_balance`, `monthly_debt_payment`; неизвестные значения `null` |
| `field_evidence[]` | `field`, `document_id`, `page`, `source_text` для каждого заполненного поля |
| `additional_facts[]` | Отдельные дополнительные факты с документом и страницей; **не** передаются в форму подтверждения профиля |
| `conflicts[]` | Поле, описание противоречия и исходные документы |
| `missing_fields[]` | Имена полей профиля со значением `null` |
| `case_id`, `model`, `synthetic` | Идентификатор сценария, модель LLM, демонстрационный признак |

Сервер проверяет наличие цитируемого текста на указанной OCR-странице и требует `field_evidence` для каждого заполненного поля. OCR и LLM не подтверждают подлинность документа.

## Работа сотрудника

### `POST /v1/underwriting/summary`

Бэк передаёт **готовый** снимок: `case_id`, `business` (`segment: micro|small`, `legal_form`, `business_age_months`, `industry`), `application` (`product_id`, сумма, срок, цель), `financials` (выручка, маржа, долговая нагрузка), `scoring` (вероятность, группа, факторы, версия), а также `checks[]` и `additional_facts[]`. `checks[].status` — `clear`, `flag` или `missing`; идентификаторы проверок и дополнительных фактов должны быть уникальны.

Ответ: `overall_assessment` (`level`, `summary`, `evidence`), массивы `strengths`, `risks`, `missing_data`, `next_actions` с текстом и путями `evidence`, `decision_complexity`, `analyst_priority`, `scoring_model_version`, `model`. Сервер рассчитывает уровни по типизированным порогам; LLM пишет текст по входу. Подробная логика и пример: [Underwriting](../../src/underwriting/README.md).

### `POST /v1/decision-explainer/refusal`

Вызывать только после выбора сотрудником «отказать» в CRM. Вход: `decision: "declined"`, полный объект `underwriting` из предыдущего маршрута, опциональный `scoring` с той же `model_version`. Ответ: только `{ "message": "..." }`, до 500 символов. Текст строится по рискам резюме; положительные вклады скоринга используются как пояснение лишь при связи с этими рисками. Пустой список рисков даёт `422`, ссылка LLM на чужой риск — `502`. Решение и статус заявки здесь не меняются.

### `POST /v1/crm-copilot/reply`

Обязательны `case_id` и `customer_question`. Можно передать `history[]`, `application`, `profile`, `scoring`, `checks[]`, `documents[]`, `underwriting`, `verified_facts[]`, `required_fields[]`. Каждый `required_fields` задаёт `path`, `label`, `reason`, `obtain_from` (`customer`, `employee`, `backend`, `document`, `check`) и необязательные `acceptable_values[]`. Бэк выбирает обязательные поля для **конкретного** вопроса; сервис независимо от LLM проверяет их наличие и допустимые значения.

Ответ: `answerability: ready|needs_data`, `summary`, `summary_evidence[]`, `missing_data[]`, `next_actions[]`, `reply_draft`, `reply_evidence[]`, `requires_employee_confirmation: true`, `model`, `synthetic`. При `needs_data` сервер формирует запрос уточнений и оставляет `reply_evidence` пустым. Клиентское сообщение из истории не считается подтверждённым фактом. Пример: [CRM Copilot](../../src/crm_copilot/README.md).

## После отказа

### `POST /v1/offer-recovery/recommendations`

Вход: `case_id`; `profile` по полям Credit Advisor; непустые `declined_offers[]` (`product_id`, отклонённая сумма и срок, `reasons[]`); непустые кредитные `recommended_product_ids[]`; `minimum_acceptable_amount` и `minimum_acceptable_term_months`. Минимально приемлемые значения не могут быть выше исходных. ID рекомендованных продуктов уникальны.

Сервис перебирает суммы и сроки по `RecoveryConfig`, проверяет правила продуктов, исключает уже отклонённые сочетания и сравнивает риск с **последним** отказом. Ответ: `variants[]` (`product_id`, `suggested_terms`, `risk_probability`, `risk_band`, `risk_change_vs_original`, `model_version`, `explanation`), `unavailable_products[]`, `declined_reasons[]`, `estimate_type: "synthetic_risk_probability"`. Отрицательный `risk_change_vs_original` означает снижение модельного риска, а не гарантированное одобрение. OpenRouter и HTTP-вызов скоринга не используются.

## Ассистент по знаниям

### `POST /v1/assistant/search`

Вход: `query` и необязательный `limit` (1–20, по умолчанию 5). Ответ — массив `{document, score}`; у документа есть `knowledge_id`, `title`, `text`, `category`, `source_url`, `effective_at`. Поиск объединяет Qdrant и BM25. Пустой по смыслу вопрос может дать `422` после доменной проверки.

### `POST /v1/assistant/answer`

Тот же вход `query`, `limit`. Сервис получает контекст через поиск, передаёт его OpenRouter и возвращает `answer`, `sources[]`, `model`, `usage` (`input_tokens`, `output_tokens`). Ответ должен цитировать хотя бы один `knowledge_id` **из переданного** набора; отсутствие или чужой ID даёт `502`. Наличие ссылки проверяет происхождение, но не доказывает верность интерпретации.

## Статусы ошибок и повторные вызовы

| HTTP | Причина | Действие клиента |
| --- | --- | --- |
| `200` | Запрос обработан; возможен пустой список рекомендаций | Разобрать ответ по контракту |
| `422` | Pydantic-валидация или доменное ограничение | Исправить вход; автоматический повтор того же тела не поможет |
| `502` | Неверный формат или недопустимые ссылки/ID в ответе LLM | Не показывать текст клиенту, передать кейс сотруднику или повторить генерацию |
| `503` | Нет ключа или недоступен OpenRouter | Повторить после восстановления провайдера/конфигурации |

API не вводит idempotency key и не сохраняет результаты. Повторный вызов локального движка на тех же данных воспроизводим; текст LLM может отличаться. Для обработки реальной заявки потребуются отдельные хранение, авторизация, аудит и банковский Decision Service, которых в прототипе нет.
