# Помощник кредитного аналитика

`POST /v1/underwriting/summary` получает **готовый снимок заявки** от бэка и составляет структурированное резюме сотруднику. Сервис не запускает скоринг, не делает проверки ФНС/БКИ и не принимает решение по кредиту.

## Контракт

| Блок запроса | Содержание |
| --- | --- |
| `case_id` | Демонстрационный ID вида `DEMO-*` |
| `business` | `segment: micro|small`, `legal_form: ip|ooo`, возраст в месяцах, отрасль |
| `application` | Кредитный `product_id`, сумма, срок в месяцах, цель |
| `financials` | Месячная выручка, чистая маржа в процентах, долг к выручке |
| `scoring` | Готовые `risk_probability`, `risk_band`, `factors[]`, `model_version` |
| `checks[]` | ID, название, `status: clear|flag|missing`, детали и источник |
| `additional_facts[]` | Дополнительные значения с уникальным `fact_id` и источником |

Ответ содержит `overall_assessment`, `strengths[]`, `risks[]`, `missing_data[]`, `next_actions[]`, `decision_complexity`, `analyst_priority`, `scoring_model_version`, `model`. Каждый вывод LLM включает `text` и `evidence[]` с путями к реально переданным полям. Это происхождение факта, а не гарантия верной интерпретации. Аналитик проверяет текст перед использованием.

## Как формируется результат

1. Сервер строит допустимые пути к полям снимка и отправляет обезличенный контекст в OpenRouter.
2. Pydantic проверяет JSON модели; сервер отклоняет ссылки вне входного снимка. Если модель не предложила действия при `missing` или `flag`, сервер добавляет действие по названию проверки.
3. Сервер независимо от LLM назначает `overall_assessment.level`, сложность и приоритет по конфигурации `config.py`.

| Показатель | Правило демонстрационной конфигурации |
| --- | --- |
| `overall_assessment.level` | `insufficient_data` при отсутствии проверок или хотя бы одном `missing`; иначе `concerning` при `flag` или риске ≥ 0.65; `mixed` при риске ≥ 0.35; иначе `positive` |
| `decision_complexity.level` | `high` без проверок, при ≥ 2 проблемных проверках или риске ≥ 0.65; `medium` при одной проблеме или риске ≥ 0.35; иначе `low` |
| `analyst_priority.level` | Сумма / месячная выручка: для `micro` пороги 1 и 2 месяца, для `small` 2 и 4. Риск ≥ 0.35 поднимает минимум до `medium`; высокий риск вместе со средним относительным размером — до `high`. Нулевая выручка даёт `high` из-за неопределённости |

`analyst_priority` — приоритет внимания аналитика, а не ценность клиента. Пороговые числа демонстрационные и не представляют банковскую политику.

## Пример сценария

В `tests/test_api.py` есть полный синтетический JSON: `DEMO-001`, ИП с выручкой 800 000 ₽, суммой 2 000 000 ₽, готовым скорингом `0.72` и проверкой обязательств со статусом `missing`. Ожидаемый `overall_assessment.level` — `insufficient_data`, `decision_complexity.level` — `high`, `analyst_priority.exposure_months` — `2.5`. Точный ответ LLM зависит от модели; уровни считаются локальными правилами.

## Ошибки и проверка

Неверный снимок даёт `422`; ответ LLM с неверным JSON или чужим `evidence` — `502`; отсутствие ключа или сбой OpenRouter — `503`. `uv run pytest -q tests/test_underwriting.py tests/test_api.py` проверяет схему, классификации и HTTP-сценарий с подменным LLM-клиентом. Живую генерацию можно проверить в `/docs` после настройки `OPENROUTER_API_KEY`.
