# Объяснение отказа

Сотрудник CRM сначала выбирает **«отказать»**, затем нажимает «Сформировать причину». `POST /v1/decision-explainer/refusal` возвращает один черновик сообщения предпринимателю. Сервис не принимает решение и не меняет статус заявки.

## Вход и выход

```json
{
  "decision": "declined",
  "underwriting": "полный JSON из /v1/underwriting/summary",
  "scoring": "необязательный готовый объект scoring из снимка"
}
```

В примере строки обозначают вложенные объекты, а не буквальные значения для отправки. Полный рабочий запрос строится в `tests/test_api.py`. `scoring.model_version` должен совпасть с `underwriting.scoring_model_version`.

Ответ содержит только `message` длиной до 500 символов. Это черновик для проверки сотрудником, не автоматическая отправка клиенту.

## Основания текста

1. Из резюме берутся только `underwriting.risks[]`. Если рисков нет, объяснение не создаётся.
2. Положительные вклады скоринга используются как дополнительное пояснение только при связи признака с `evidence` этих рисков. Положительный `contribution` повышает логит риска; числовой вес и внутренний порог в текст клиенту не передаются.
3. OpenRouter получает индексы рисков и возвращает сообщение с `risk_indexes[]`. Сервер проверяет, что индексы относятся к переданным рискам и не повторяются.

Текст не должен обещать одобрение при повторной подаче или добавлять причины, которых не было в резюме. Проверка индексов подтверждает источник, но сотрудник всё равно оценивает смысл сообщения.

## Ошибки и проверка

Неверное значение `decision`, несовпадающая версия скоринга или отсутствие рисков дают `422`. Неверный ответ модели или ссылка на чужой риск дают `502`; недоступный OpenRouter — `503`. Проверка: `uv run pytest -q tests/test_decision_explainer.py tests/test_api.py`. Интеграционный тест использует синтетический отказ и подменную LLM.
